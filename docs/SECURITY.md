# Security notes

The API accepts structured geospatial files, which are untrusted input. The controls below reduce
common risks but do not replace deployment isolation, dependency maintenance, and monitoring.

## Implemented controls

- Only KML and ZIP extensions are accepted; KML and ZIP content receive structural checks.
- Declared oversized multipart requests are rejected in middleware before form parsing. File bytes
  are also checked while being copied to storage.
- ZIP path traversal, absolute paths, encrypted members, too many entries, and excessive expanded
  size are rejected. Shapefile components are extracted under fixed filenames in a temporary
  directory; archive member names are never used as filesystem paths.
- Client filenames are sanitized for display. Internal storage names are generated by the service
  and are not returned in API responses.
- KML documents containing a `DOCTYPE` declaration in the inspected prolog are rejected. Geospatial
  files are parsed, never executed.
- Errors returned to clients do not expose GDAL messages, server paths, or unexpected exception
  details. Unexpected errors and request/job identifiers are retained in server logs.
- In production, `/api/` routes require a non-empty `API_KEY` sent as `X-API-Key`, and requests are
  subject to a Redis-backed fixed-window limit per client host as seen by the ASGI server. The
  production key must be at least 32 characters. The limiter fails closed if Redis is unavailable.
  If deployed behind a proxy, configure trusted proxy handling deliberately before using forwarded
  client-address headers.
- The repository excludes local `.env` files, local databases, temporary uploads, Python caches,
  and build/test artifacts through `.gitignore`.

## Deployment requirements and limitations

- Enforce a total request-body limit at the reverse proxy or ingress. The application can reject an
  oversized declared `Content-Length` early, but a proxy must also constrain requests that omit or
  misstate it.
- Run the service behind TLS. Store `API_KEY`, database credentials, and Redis credentials in the
  deployment secret manager; do not reuse the local Compose credentials.
- The API key is shared across the service and does not provide per-user identity or file ownership.
  Do not use this configuration as multi-tenant authorization.
- No antivirus scanner is bundled. If the service accepts files from untrusted public users, add a
  malware-scanning step and run native geospatial parsing with appropriate CPU, memory, process, and
  filesystem limits. Restrict worker outbound network access unless the deployment has a clear need
  for it, particularly when processing KML with external references.
- Worker and reconciler need access to upload storage. Restrict that volume to the service account
  and back it with storage appropriate to the deployment.
- Keep Python, GDAL/PROJ/GEOS, PostgreSQL/PostGIS, and application dependencies updated. Review
  vulnerability advisories as part of the release process.
